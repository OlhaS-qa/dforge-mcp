# Discovery — how to ask

Phrasing and typical proposals for each topic of `SKILL.md`. The proposals come from the quiet draft of Step 2. Adapt the nouns to the
user's business; keep the shape (restate, propose numbered, ask for corrections).

## Wording rules

| Do | Do not |
|---|---|
| "Understood: requests are in a paper log and get lost." | Start with "Accepted:" or repeat a long summary |
| "Usually it works like this, correct me: 1 … 2 … 3 …" | Offer a menu of choices as if the user had to pick a role or a template |
| "The system can tell people when something happens: in the system (they see it when they log in) or by e-mail." | Mention triggers, jobs, mail providers, modules, templates, search |
| "By your words the main thing is that requests do not get lost and it is clear who is responsible. What else should get better after launch?" | Ask again what they have already said; add conditions ("a system this size should be simple") |
| One short question about one thing | Three questions in one block (for example scale, goals, how it works now) |
| "Do you already have a form? Send a sample or list its fields: we will check every field against the system." | Promise "exactly the fields of your paper" |

## Step 3 — business analysis

1. _How are these things handled now, and what bothers you most?_ (open)
2. _By your words the main thing is …. What else should get better a month after launch?_ Offer one or two typical goals of the domain.

## Step 4 — details

**People and visibility (free prose first).** _Who will work with the system and what does each kind of person do?_ Then, as verbs: _What should each of them see when they open the system: which records, and which can they change?_ Restate as sentences like "Workers raise requests and see only their own until they are taken into work." No role names offered.

**Lifecycle.** Propose the typical statuses of the domain and the usual refusals, numbered:
_Usually a record goes New → In progress → Done → Closed, and can be Cancelled. Typical rules: 1) only X can close it, and only when it is done; 2) it cannot be taken into work without Y; 3) cancelling needs a reason; 4) records are not deleted, only cancelled. Is this how it is for you? Can a finished record be sent back, and with a reason?_

**Calculated values.** _The system can calculate these without anyone typing them: 1) a running number such as RM-2026-0001; 2) duration or downtime; 3) overdue flag (after how many hours/days?); 4) cost; 5) stock after use. Which do you need?_ Ask only for the values that follow from the entities.

**Notifications.** The table below is your source, not a list to offer in full: take at most five events that serve a named pain, then ask who else must be told. For each date with a deadline and each status change, propose the event and the person told (see the table). Then: _Which are needed? Which only in the system, which also by e-mail?_

| Trigger | Typical recipient |
|---|---|
| New record | whoever takes it into work |
| Taken into work | whoever raised it |
| Waiting for something | the person responsible for the stage |
| Finished | whoever closes or accepts it |
| Sent back | the previous doer, with the reason |
| Overdue (deadline passed, not closed) | the responsible person, usually also by e-mail |
| Expiring document or licence | the person who manages it, N days ahead |
| Low stock | whoever orders |

**Documents and files.** _Besides the screens, the system can produce documents for printing, spreadsheets and exports. Usually people need: 1) … 2) … 3) …, and sometimes a file to pass to another program. Which do you need and is there anything else? If you already have a form, send a sample or list its fields._ After the sample arrives, compare it with the fields already agreed, say in one line that the rest is already there, and ask only about the missing fields as a numbered list. Ask who signs and whether signatures are on paper or in the system.

**Initial data.** _What must be in the system at the start: 1) … 2) …. For each: is there a table, will you enter it by hand, or start empty — and roughly how many records?_

## Step 5 — reports and scenarios

Reports, each as: _For whom — what decision it helps to make — default period._ Example: "For the section head: which equipment loses the most time and why — last month."

Scenarios, as: a title, steps from the user's point of view, the expected result. Cover: the main path from raising to closing, a second main path (for example a request sent back), and refusals: acting on a record in the wrong status, a missing required value, a duplicate, cancelling without a reason.

## When the user does not know

Offer the typical answer and record it as `typical`. If there is no typical answer, record it as an open question; never fill it silently.
